## 1. Контекст и входные данные

Вопрос: как различаются заявленные суточные цены и календарная доступность между
районами Амстердама при сравнении одинаковых типов жилья?
Основание — [Project Brief](project_brief.md). Строка — объявление, ключ — `id`
внутри одного снимка. Источник — Inside Airbnb, версия 2026-06-15.

Путь для основного ноутбука:
`s3://raw/airbnb_amsterdam_listings/ingested_on=2026-10-23/listings.csv.gz`.
Объект должен быть загружен DAG ЛР № 2 с логической датой **2026-10-23**.
Фактический сбор — **15–24 июня 2026**. Дата ingestion не является датой сбора.
Основной ноутбук читает CSV непосредственно из S3; диагностическая копия использует
`data/source/listings.csv.gz` и сохраняется отдельно.

## 2. Профиль исходных данных

**10 369 строк, 90 исходных полей, 22 района.** Ключи заполнены и уникальны:
0 повторяющихся ключей, 0 избыточных строк (Σ(n−1) по повторяющимся непустым ключам).
Типы определены DuckDB по всему CSV до нормализации; исходные значения в памяти
сохраняются как текст для точного представления в карантине.

| Поле | Тип DuckDB; пример | Проверено | Пропусков | Доля |
|---|---|---:|---:|---:|
| neighbourhood_cleansed | VARCHAR; Centrum-West | 10 369 | 0 | 0% |
| room_type | VARCHAR; Entire home/apt | 10 369 | 0 | 0% |
| price | VARCHAR; $143.80 | 10 369 | 3 992 | 38,50% |
| availability_365 | BIGINT; 0, 365 | 10 369 | 0 | 0% |
| has_availability | BOOLEAN; исходные t/f | 10 369 | 136 | 1,31% |

Пропуск — NULL/пустая строка после trim, знаменатель — все строки. Отсутствующая
цена ограничивает ценовой анализ, неизвестный календарный признак — основной
фильтр доступности. Даты `last_scraped` и `calendar_last_scraped` имеют минимум
**2026-06-15**, максимум **2026-06-24**; значений вне заданного периода нет.
Сбор объявлений по датам: 15 июня — 499, 16 июня — 6 450, 24 июня — 3 420.

| Тип жилья | Объявлений |
|---|---:|
| Entire home/apt | 8 489 |
| Private room | 1 833 |
| Hotel room | 26 |
| Shared room | 21 |

Два наблюдения: **38,50% цен отсутствует**, поэтому будущие медианы описывают только
предложения с известной корректной ценой; **редкие типы жилья малочисленны**, а
разделение по районам ещё уменьшит группы. Пропуски нельзя заменять нулём.

## 4. Подготовленные данные

Префикс назначения в S3:
`s3://staging/airbnb_amsterdam_listings/source_ingested_on=2026-10-23/`.
Результаты — `staging.parquet` и `quarantine.parquet`.
Локально оба Parquet созданы и прочитаны обратно: **10 369 = 10 369 + 0**.
Критических нарушений в подготовленном наборе нет, четыре флага проверены.
Копии результатов находятся в `docs/evidence/`; они не заменяют объекты на SeaweedFS.

Нормализация: id сохраняется строкой; удалены внешние пробелы категорий;
цена → `price_eur DECIMAL(14,2)` (EUR по Brief), доступность → INTEGER,
признак календаря → BOOLEAN. Исходные значения преобразованных полей сохранены
в `*_source`. Флаги `flag_price_missing`, `flag_price_invalid`,
`flag_calendar_unknown`, `flag_calendar_inconsistent`: true означает нарушение.
Бизнес-агрегаций нет. Пустой карантин имеет схему с 90 исходными полями,
номером строки, `quality_rule_ids` (id через `;`) и `quarantine_reason`.
Карантин имеет приоритет, несколько причин не размножают строку.
